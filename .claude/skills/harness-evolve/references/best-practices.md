## 2. 에이전트 설계 기준

### 모델 선택 가이드
| 작업 유형 | 권장 모델 | 이유 |
|----------|---------|------|
| 코드 리뷰 (체크리스트) | Sonnet | 정형 작업, 비용 효율 |
| SQL 쿼리/분석 | Sonnet | 패턴화된 작업 |
| DDL/마이그레이션 | Sonnet | 규칙 기반 생성 |
| 문서 동기화 | Haiku | 단순 텍스트 처리 |
| 타입 검증 (tsc) | Haiku | 명령 실행 + 파싱 |
| UI/UX 평가 | Sonnet | 레퍼런스 기반 판단 |
| 복잡한 아키텍처 설계 | Opus | 다중 제약 추론 (드물게) |

**원칙:** Sonnet 기본, Haiku 단순작업, Opus는 5% 미만만.

### 역할 분리 원칙
- **보조 에이전트**: 읽기 전용 (리뷰, 분석, 검증) → permissionMode: plan
- **실행 에이전트**: 코드 수정 가능 → permissionMode: acceptEdits
- **팀 워커**: 구현 담당, worktree 격리(파일 작업만, DB 제외)
- 하나의 에이전트 = 하나의 명확한 역할 (중복 금지)

### permissionMode 가이드
| 모드 | 용도 | 에이전트 예시 |
|------|------|-------------|
| plan | 읽기 전용 분석 | reviewer, analyst, migrator(초안) |
| acceptEdits | 파일 수정 자동 승인 | doc-syncer, api-worker, ui-worker |
| dontAsk | 자동화/CI | test-runner (Bash만) |

### worktree 격리 기준
- **사용**: 파일 수정하는 병렬 에이전트 (api-worker, ui-worker, reviewer)
- **미사용**: 공유 자원 직접 접근 (DB 실행), 읽기 전용, 백그라운드 문서화
- DB 작업은 worktree 격리 불필요 (Supabase는 공유 자원)

### maxTurns 가이드
| 에이전트 유형 | 권장 | 이유 |
|-------------|:---:|------|
| 읽기 전용 (분석/리뷰) | 10-15 | 무한 루프 방지 |
| 구현 워커 | 15 | 태스크 1-3개 기준 |
| 검증 (tsc) | 10 | 단순 명령 실행 |
| 문서 동기화 | 15 | 다수 파일 업데이트 |

## 3. 에이전트 팀 설계 기준 (Lv.4)

### 팀 사용 조건
- 독립적 태스크 (P) 3개 이상
- 2개 이상 영역 (DB, API, UI) 에 걸친 작업
- 순차 의존성이 적고 병렬화 이점이 큰 경우

### 팀 크기
| 등급 | 팀원 수 | 판정 |
|:---:|:---:|:---:|
| A | 3-5명 | 최적 (조율 오버헤드 ↔ 병렬성 균형) |
| B | 6-8명 | 대규모 프로젝트만 |
| C | >8명 | 과다 (조율 비용 > 병렬 이점) |

### 워커 역할 분리
| 워커 | 담당 | 도구 | 격리 |
|------|------|------|:---:|
| db-worker | DB 마이그레이션 실행 | Read, Write, Edit, MCP postgres | 없음 |
| api-worker | API route.ts 구현 | Read, Write, Edit, Bash | worktree |
| ui-worker | UI 컴포넌트 구현 | Read, Write, Edit | worktree |

### 의존성 순서
```
db-worker 완료 → api-worker 시작 → ui-worker 시작
(의존성 없는 태스크는 병렬)
```

### 보조 에이전트와의 분리
| 보조 에이전트 | 팀 워커 | 차이 |
|-------------|---------|------|
| db-migrator (SQL 초안) | db-worker (실행) | 읽기 vs 쓰기 |
| ui-ux-expert (평가) | ui-worker (구현) | 리뷰 vs 구현 |
| test-runner (검증) | — | 구현 후 체인 |

### 안티패턴
- 단순 순차 작업에 팀 사용 (토큰 낭비)
- DB 워커에 worktree 격리 (공유 자원이므로 무의미)
- 보조 에이전트와 워커 역할 중복
- 팀원 8명 이상 (조율 오버헤드)
- 브로드캐스트 남용 (팀원 수 × 토큰)

## 5. 스킬 설계 기준

### 크기 제한
- SKILL.md: **500줄 이내** (초과 시 분할)
- 레퍼런스: `references/` 하위 파일로 분리
- `!cat` 동적 로드: `head -N`으로 크기 제한

### 타입 구분
| 타입 | user-invocable | 용도 |
|------|:-:|------|
| 작업 스킬 | true | `/deploy`, `/audit` 등 명시적 실행 |
| 참조 스킬 | false | 에이전트가 자동 로드하는 배경지식 |

### allowed-tools
- 최소 권한 원칙: 필요한 도구만 나열
- 읽기 전용 스킬: `Read, Grep, Glob`만
- 실행 스킬: `Bash(명령)` 형태로 명령 제한

### 에이전트 skills 필드
- 에이전트에 불필요한 스킬 연결 금지 (컨텍스트 낭비)
- 예: doc-syncer에 feature-planning 스킬 → 불필요

## 6. 훅 설계 기준

### 필수 PreToolUse 훅 (모든 프로젝트)
| 훅 | 목적 |
|----|------|
| SQL 안전 | DROP/TRUNCATE + WHERE 없는 DELETE/UPDATE 차단 |
| .env 보호 | 환경변수 파일 수정 차단 |
| git push 재확인 | 무의식적 push 방지 |
| 빌드/배포 차단 | 명시적 요청만 허용 |

### 훅 타입별 가이드
| 타입 | 용도 | 토큰 소비 |
|------|------|:---:|
| command | 확정적 규칙 (패턴 매칭) | 없음 |
| prompt | LLM 판단 필요 | 매 실행 시 소비 |
| agent | 복잡한 조사 필요 | 높음 |

### 안티패턴 (1M 컨텍스트 시대)
- **빈번 이벤트(Stop, PostToolUse)에 prompt/agent 타입**: 매 실행마다 LLM 호출 → 레이턴시 + 비용
- **Stop 훅에 무거운 작업 (tsc 전체 빌드)**: 질문 답변에도 30초 대기 → test-runner 에이전트로 대체
- **훅 12개 이상**: 매 도구 실행마다 체감 느려짐
- `*` matcher에 비싼 훅: 모든 도구 호출마다 실행
- async 훅으로 차단 시도 (async는 info-only)
- 토큰 절약 목적의 과도한 최적화: 1M에서는 레이턴시가 더 중요

## 10. 하네스 자가 평가 시스템

### 정량 감사 (harness-audit)
- 모든 하네스 파일을 자동 수집하여 메트릭 측정
- 7축 점수 자동 산출 (간결성/레이턴시/보안/컨벤션/적합성/에이전트팀/워크플로우)
- 이전 감사 결과와 Before/After 비교

### 컨벤션 드리프트 감지
- rules/*.md에서 규칙 추출 → 실제 코드에서 위반 사례 grep
- 확실한 위반만 보고 (false positive 최소화)
- 자동 수정 가능 건은 사용자 승인 후 일괄 수정

### 자기참조적 개선 루프 (Phase 3)
| 단계 | 행위 | 산출물 |
|------|------|--------|
| 감사 | harness-audit 실행 | 정량 리포트 |
| 개선 | Phase 2 제안 적용 | 수정된 파일 |
| 재감사 | harness-audit 재실행 | Before/After 비교표 |
| 기록 | memory에 결과 저장 | 감사 이력 |

### 감사 빈도 권장
| 등급 | 빈도 |
|:---:|------|
| A | 월 1회 (유지 확인) |
| B+ | 격주 (개선 추적) |
| B 이하 | 주 1회 (집중 개선) |

### 에이전트 성능 추적
- 에이전트 상태 코드(DONE/DONE_WITH_CONCERNS/BLOCKED) 비율 관찰
- DONE_WITH_CONCERNS 빈도 높은 에이전트 → 프롬프트 개선 대상 플래그
- 감사 시 에이전트별 프롬프트 품질도 평가 (200단어 이상, 체크리스트 포함 여부)

## 12. 커뮤니티 패턴 채택 평가 프레임워크

> harness-evolve Phase 2에서 외부 패턴을 동적 탐색할 때 사용하는 평가 기준.
> 특정 레포를 고정 참조하지 않는다 — **매번 최신 인기 레포를 탐색**하여 신선한 패턴을 발굴한다.

### 12.1 탐색 프로세스

1. **검색**: WebSearch로 `"Claude Code" agents skills hooks best practices {현재년도}` + `site:github.com "claude code" stars:>1000` 등 복수 쿼리
2. **선별**: 검색 결과에서 Stars 상위 5~10개 레포 식별 (GitHub API로 실제 Stars 확인)
3. **내용 추출**: 각 레포의 README, CLAUDE.md, .claude/ 구조를 WebFetch로 읽기
4. **패턴 추출**: 우리 하네스에 없는 새로운 패턴/기법 식별
5. **평가**: §12.2 기준으로 채택 여부 판단
6. **제안**: 통과한 패턴만 사용자에게 제안 (최대 3개)

### 12.2 채택 판단 기준 (5점 척도)

| 기준 | 가중치 | 설명 |
|------|:---:|------|
| **실익** | 30% | 토큰 절감, 레이턴시 감소, 품질 향상 등 측정 가능한 이점이 있는가? |
| **적합성** | 25% | 우리 프로젝트 규모/도메인(ERP, 정형 업무)에 맞는가? |
| **검증도** | 20% | Stars 수, 이슈/PR 활성도, 실제 사용 후기가 있는가? |
| **도입 비용** | 15% | 기존 하네스 수정 범위가 작은가? 파괴적 변경 없는가? |
| **중복 여부** | 10% | 우리가 이미 유사하게 구현한 것은 아닌가? |

### 12.3 채택 판단 결과

| 총점 | 판정 | 행동 |
|:---:|:---:|------|
| 4.0+ | ✅ 채택 권장 | 제안에 포함 |
| 3.0-3.9 | 🟡 검토 | 사용자에게 트레이드오프 설명 후 판단 위임 |
| <3.0 | 🔴 미채택 | 제안에서 제외, 사유만 기록 |

### 12.4 안티패턴 (탐색 시 주의)

- **Stars만 보고 채택**: 100k★이어도 우리 규모에 과도할 수 있음 (적합성 우선)
- **전체 프레임워크 도입**: 개별 패턴만 선별 채택 — 프레임워크 종속 금지
- **유행 추종**: 최근 급등 레포는 검증 부족할 수 있음 — 3개월 이상 유지된 Stars 기준
- **이미 있는 것 재도입**: 이름만 다르고 우리 구현과 동일한 패턴 무시
- **고정 목록 의존**: 같은 레포만 반복 참조하지 말고 매번 새로 검색
